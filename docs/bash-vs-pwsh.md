# Windows 終端機比較:pwsh、git bash,以及 `MSYS_NO_PATHCONV`

## 摘要

比較對象有三個,都是「已套用設定檔」的狀態:

1. **pwsh(+ `$PROFILE`)**:`$PROFILE` 目前不用再動。
2. **bash(+ bashrc)**:`MSYS_NO_PATHCONV` 不設(等於 `=0`,MSYS 自動轉換路徑)。
3. **bash(+ bashrc,`MSYS_NO_PATHCONV=1`)**:現況。

兩個 shell 慣用的寫法本來就不同(pwsh 用 `$env:TEMP`、`[IO.File]::WriteAllText`、here-string;bash 用 `$TMPDIR`、`printf`、heredoc、`/dev/null`)。**每個 shell 只算它自己的寫法會踩到的坑**,不拿 A 的語法去量 B。

結論:

- **pwsh 比 bash 好。** pwsh 的坑多半是解析階段就報錯,訊息明確;bash 的坑常常 exit 0,並在 cwd 或非預期位置留下檔案。後者 bashrc 修不了。
- **bash 的兩種設定,加上同一份 bashrc 修復後,`=0` 比 `=1` 高 0.5 分。** 差距來自三個沒有機械修法的 case(資料參數、POSIX 路徑參數、環境變數前綴)。如果你的實際使用以「`/owner/repo` 這類 ID 當參數」為主,`=1` 仍會勝出,條件在第 6 節。
- **bashrc 值得加的只有兩段:** `TMPDIR`,以及 `cmd` 與具名工具的 argv 層函式。其他方案(`MSYS2_ARG_CONV_EXCL`、輸入端 lexer、移除 `where` 別名等)都試過,不採用,理由在第 8 節。

## 1. 方法與計分

### 測試方式

- 把 `record/pwsh-1/2`、`record/bash-1/2` 四份報告中的指令原樣各跑一次,不修正,不剝掉 profile。每題獨立行程,stdin 關閉,逾時 20 到 45 秒。
- 報告中兩邊用自己的慣用寫法完成的任務,都**正確執行**,不扣分:
  - pwsh:`$env:TEMP`、`[IO.File]::WriteAllText`、`Set-Content -LiteralPath`、here-string 管線餵 `python -`、中文參數與中文 stdin、`> nul`、未加引號的 Windows 路徑重導。
  - bash:`printf`、`cat`、heredoc、`tee`、`/dev/null`、中文參數與中文檔名。
- bash 的 `-c` 與 `-l` 不同:`-c` 時 `$TMPDIR` 是空的,`-l` 時是 `/tmp`。報告用的是 `-c`,所以 `TMPDIR` 相關結論以 `-c` 為準。
- MSYS 轉換行為對照時,用 `env` 移除 `BASH_ENV` 與 `MSYS_NO_PATHCONV`,避免 bashrc 把設定加回來。
- 環境:Git for Windows 2.56.0.4、pwsh 7.6.9。pwsh 的 console 與 `$OutputEncoding` 都是 UTF-8(65001)。

### 計分規則

以「預期正確」為基準,正確不給分,只算偏離。**每一步最多 0.5 分**:

| 狀態                                                                                                         | 距離正確幾步 | 記法   |
| ------------------------------------------------------------------------------------------------------------ | ------------ | ------ |
| ✅ 正確                                                                                                       | 0            | 0      |
| ⚠️ 顯示具體錯誤,可從訊息修正                                                                                  | 1            | −0.5   |
| ❌ 靜默失敗(含 exit 0 的假成功、超時)                                                                         | 2            | −0.5×2 |
| 💥 額外傷害:建立或刪除非預期檔案、寫到非預期位置、終止非預期行程等。**無論有沒有顯示錯誤訊息,一律這個分數。** | 3            | −0.5×3 |

- **修復加分** = 0.5 × 修復跨越的步數 × 覆蓋率 `c`。例如把 ❌ 修成 ✅ 是兩步,最多 +0.5×2;只修了 10/1000 的寫法,就乘 10/1000。
- **副作用**:預期正確的流程被改成顯示錯誤,扣 0.5。
- **同一個失敗機制的寫法變體只算一個 case,取最嚴重的狀態。**
- **開放集合規則**:修復若需要窮盡 bash 語法(開放集合),誤修會弄壞合法語法,保守則漏修無限增長,一律算負無限,不採用。
- 錯誤訊息裡出現「使用者沒打過的字」仍算 ⚠️,因為程式確實收到了那個值。如果把這類訊息改算 ❌,`=1` 相對於 `=0` 會更有利。
- 覆蓋率 `c`(cmd 函式)與 `c₃`(具名工具包裝)**沒有真實的出現頻率數據**,保留成變數,只給範圍,不編數字。

### 哪些不算進分數

- **錯用語法:** 把一個 shell 的語法打進另一個 shell(例如在 pwsh 裡打 `echo %TEMP%`、在 bash 裡打 `dir /b`),屬於寫法選錯,不是 shell 的缺陷,列在第 9 節,不計分。
- **cmd 端行為:** 同一個字串送到 cmd,兩邊結果一樣的,放在第 2 節的「共同」,兩邊扣一樣的分,不影響排名。

### 文件選 `=1` 的理由,在這個計分裡的位置

`=1` 相對於 `=0` 的差異是 **−0.5**:

- `=1` 的優勢:K1 +0.5×2、K3 +0.5、K5 +0.5×2。
- `=1` 的代價:K2 −0.5×2、K4 −0.5、K6 −0.5、K7 −0.5×2。

文件的核心理由是 K5(ID 資料被靜默改寫),它在這個計分裡確實是 `=1` 最大的單項優勢。

**什麼情況下 `=1` 會勝出:** 上面是不加權的。設 f 為各 case 的出現頻率,加了 bashrc 修復後 K1~K4 的差距會抵消,剩下:

> `=1` 勝出,當且僅當 f(K5) × 1.0 > f(K6) × 0.5 + f(K7) × 1.0

你的文件說 agent 最常送的就是 `/owner/repo` 這類 ID,如果實際頻率符合,`=1` 就是對的選擇。我沒有頻率數據。

## 6. bashrc 修復:設計與程式碼

三段都是 **argv 層**的修復:函式看到的是 bash 解析完引號、拼接之後的最終參數。這決定了它們的 edge case 是否有限。

實測的 argv 形狀(原生程式實際收到的值):

| 寫法                       | 原生程式收到             | 結論                                |
| -------------------------- | ------------------------ | ----------------------------------- |
| `"/c"`、`'/c'`             | 與 `/c` 相同             | 引號 bash 已處理                    |
| `/c"ver"`                  | 與 `/cver` 相同          | 拼接 bash 已處理                    |
| `cmd /c ver& echo after`   | bash 把 `&` 拆成兩條指令 | `&` 是 shell 層,函式看不到          |
| `///c`、`/c/`、`\c`、`/c:` | 都不是有效的 cmd 開關    | 不需要修,規則不會動它們             |
| `/cver`(附著寫法)          | cmd 接受                 | 開關形狀是「`/` + 字母 + 任意尾巴」 |

所以引號、拼接、`&`、斜線組合不會成為函式的 edge case。cmd 開關是封閉的語法,規則只在命令字等於 `cmd` 且位於第一個 `/c`、`/k` 之前才動,**不需要讀 bash 語法,不會誤修**。

會無限增長的只有**覆蓋率**:命令字的包裝寫法(`env cmd`、`timeout cmd`、`xargs`、`command cmd`、完整路徑、`$COMSPEC`)與工具名單。漏掉的結果只是維持原狀,不會比沒修更糟。這與輸入端 lexer 的本質差異在於:lexer 一旦漏修或誤修,語法本身就會壞。

### 6.1 `TMPDIR`(K8:+0.5×3,覆蓋率 1)

```bash
if [ -n "$LOCALAPPDATA" ]; then export TMPDIR="${LOCALAPPDATA//\\//}/Temp"; fi
```

- **為什麼需要:** `bash -c` 下 `$TMPDIR` 是空的,即使套用了 bashrc 也一樣。`"$TMPDIR/x"` 會悄悄變成 `/x`,落在 git 安裝目錄。
- **為什麼用 `LOCALAPPDATA` 而不是 `TEMP`:** 在 bash 裡 `TEMP` 已被轉成 `/tmp`,而 `/tmp` 傳給原生程式在 `=1` 下不會被轉換(python 實測 `isdir: False`)。`LOCALAPPDATA` 保持 Windows 形式。
- **為什麼用 `${var//\\//}`:** 純參數展開,沒有 fork。`.bashrc` 現有註解說 MSYS 的 fork 約 20ms/次,這點不能破壞。
- **結果:** 替換後為 `C:/Users/artin/AppData/Local/Temp`。bash 內建指令、python、`mktemp` 都能正確使用(實測)。
- **覆蓋率 1 的理由:** 只有一個變數,封閉。
- **代價與假設:** 假設 Temp 位於 `%LOCALAPPDATA%\Temp`(目前 `TEMP` 確實如此);login shell 原本的 `/tmp` 會被覆蓋。`if` 保護是我加的,只做了語法層面的推論,沒有單獨測。
- **不解決的事:** 直接寫字面 `/tmp/x` 傳給原生程式(K6),這是 `=1` 的代價,仍然是 ⚠️。

### 6.2 `cmd` 函式(K1、K2:各 +0.5×2·c)

```bash
_cmdsw() { local a=() sw=1 x
  for x in "$@"; do
    if [ $sw = 1 ]; then
      if [ -n "${MSYS_NO_PATHCONV+x}" ]; then case "$x" in //[A-Za-z]*) x="${x#/}";; esac
      else case "$x" in /[A-Za-z]*) x="/$x";; esac; fi
      case "${x#/}" in [cCkK]*) sw=0;; esac
    fi
    a+=("$x")
  done; command cmd "${a[@]}"; }
cmd() { _cmdsw "$@"; }; cmd.exe() { _cmdsw "$@"; }
```

設計理由:

- **同一份規則兩個方向都能用。** 以 `MSYS_NO_PATHCONV` **是否存在**(不是值)決定方向,與 MSYS 的判斷方式一致:`=1` 時把 `//c` 削成 `/c`;`=0` 時把 `/c` 補成 `//c`,再讓轉換層削回 `/c`。所以要不要換回 `=0`,和要不要裝這個函式是兩個獨立的決定。
- **`sw` 旗標。** 只處理第一個 `/c`、`/k` 之前的 cmd 開關區,命令字串本身不碰。實測 `cmd /c "echo //c stays"` 輸出原樣的 `//c stays`。
- **`[cCkK]*` 而不是精確比對。** cmd 接受附著寫法(`cmd /cver` 能動),所以只比開頭。
- **`cmd.exe` 也要定義。** 兩種寫法都常見,實測 `cmd.exe //c ver` 修好了。
- **`command cmd`。** 避免函式遞迴呼叫自己。

實測範圍(`=0` 與 `=1` 各自測過的寫法):

| 寫法                        | `=0`                              | `=1`                               |
| --------------------------- | --------------------------------- | ---------------------------------- |
| `cmd /c ver`、`cmd //c ver` | 都正常                            | 都正常                             |
| `cmd /cver`                 | 正常                              | 正常                               |
| `cmd /d /s /c "echo hi"`    | 正常                              | 正常                               |
| `cmd.exe`                   | `/c` 正常                         | `//c` 正常                         |
| `cmd //d //c "echo hi"`     | 未測                              | 正常                               |
| 命令字串內含 `//c` 或 `/c`  | `cmd /c "echo /c stays"` 原樣輸出 | `cmd /c "echo //c stays"` 原樣輸出 |
| exit code                   | `cmd /c "exit 7"` 回 7            | `cmd //c "exit 7"` 回 7            |

沒測的格子,靠同一份規則的對稱性推論,不是直接實測。

**涵蓋不到的寫法**(實測 `env cmd` 沒修好,其餘依同樣機制推論):`env cmd`、`timeout 5 cmd`、`command cmd`、`xargs`、完整路徑 `/c/Windows/System32/cmd.exe`、`$COMSPEC`。這個尾巴是開放集合,函式因此是「封閉核心加不回歸的尾巴」,不是完整解,覆蓋率 `c` 小於 1。

### 6.3 具名工具的旗標包裝(K3、K4:各 +0.5·c₃)

```bash
_sf() { local t="$1"; shift; local a=() x
  for x in "$@"; do
    if [ -n "${MSYS_NO_PATHCONV+x}" ]; then case "$x" in //[A-Za-z?]*) [[ "${x#//}" != */* ]] && x="${x#/}";; esac
    else case "$x" in /[A-Za-z?]*) [[ "${x#/}" != */* ]] && x="/$x";; esac; fi
    a+=("$x")
  done; command "$t" "${a[@]}"; }
taskkill() { _sf taskkill "$@"; }; tasklist() { _sf tasklist "$@"; }; findstr() { _sf findstr "$@"; }
```

設計理由:

- **只動「單一段、開頭是字母或 `?`」的 token。** `[[ … != */* ]]` 排除含第二個斜線的 token,所以 `//server/share` 這類 UNC 路徑、`/tmp/x` 這類真路徑不受影響。
- **為什麼是具名包裝,而不是通用規則。** bash 沒有「所有原生程式執行前」的通用鉤子;DEBUG trap 需要解析 `BASH_COMMAND` 字串,屬於輸入端 lexer,依規則是負無限。所以只能列已知工具,工具名單是開放集合,覆蓋率 `c₃` 小於 1。
- **實測:** `taskkill /IM`、`taskkill //IM`、`tasklist /FI`、`findstr /i` 在兩個模式下都正常。
- **推論但未實測的風險:** 具名工具收到「單一段 POSIX 路徑」(例如 `findstr x /tmp`),`=0` 的包裝會把它加成 `//tmp`,路徑就不再被轉換。發生機率很低。

### 修復後的 bash 專屬(MSYS)小計
